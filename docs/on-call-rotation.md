# On-Call Rotation Management

This document describes the automated on-call scheduling system implemented
in `backend/src/oncall.rs`. It replaces the previous manual, spreadsheet-based
rotation process with a generated schedule, automatic handoff notifications,
and tiered escalation policies.

## Why

On-call schedules were maintained by hand, which led to coverage gaps and
missed handoffs between rotations. Automating rotation generation removes
that class of human error.

## Concepts

- **Participant** — an engineer eligible for the rotation (`OnCallParticipant`).
- **Shift** — a single scheduled on-call window (`OnCallShift`), generated by
  round-robin assignment across participants for a configured number of
  hours (`rotation_hours`).
- **Handoff notification** — automatically generated whenever one shift ends
  and the next begins (`HandoffNotification`), recording the outgoing and
  incoming engineer.
- **Escalation policy** — an ordered list of tiers (`EscalationLevel`), each
  with a delay and a set of contacts to notify if the current on-call has not
  acknowledged an alert.

## API

### `POST /admin/on-call-schedule`

Creates a new rotation schedule.

```json
{
  "name": "platform-primary",
  "participants": [
    { "id": "u1", "name": "Alice", "contact": "alice@example.com" },
    { "id": "u2", "name": "Bob", "contact": "bob@example.com" }
  ],
  "rotation_hours": 168,
  "shift_count": 6,
  "escalation_policy": {
    "levels": [
      { "level": 1, "delay_minutes": 5, "contacts": ["alice@example.com"] },
      { "level": 2, "delay_minutes": 15, "contacts": ["bob@example.com"] }
    ]
  }
}
```

Returns `201 Created` with the generated `OnCallSchedule`, including all
shifts and the handoff notifications produced for each shift boundary.

### `GET /admin/on-call-schedule`

Lists all schedules currently stored.

### `GET /admin/on-call-schedule/:id`

Fetches a single schedule by id.

### `POST /admin/on-call-schedule/:id/escalate`

Manually triggers the next escalation tier above `current_level` (e.g. when
an alert has gone unacknowledged past its delay window). Returns which level
fired and the contacts that were notified.

## Rotation algorithm

`build_rotation` assigns participants to shifts in round-robin order, each
shift lasting `rotation_hours` starting from the previous shift's end time,
beginning at the current time. `build_handoffs` then walks consecutive shift
pairs and emits one `HandoffNotification` per boundary.

## Operational notes

- The current implementation stores schedules in-memory
  (`Arc<Mutex<HashMap<...>>>`); a durable store should back this before
  relying on it across process restarts.
- Escalation delivery is logged via `tracing`; wiring it to the existing
  `notifications` module (SMS/push) is a follow-up.
